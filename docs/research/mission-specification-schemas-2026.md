# Mission specification schemas: how to define a drone mission sustainably

Researched 2026-09-10/11. Scope: given a fully automated OpenDroneMap/splatfacto pipeline and DJI WPML KMZ as the only thing the DJI Mini 5 Pro + RC2 (DJI Fly) can actually fly, what vocabulary and file format should this business use as the **source of truth** for a mission — the area, the objects/structures of interest, the flight pattern, and every per-waypoint detail (position, height reference, heading/POI, gimbal, actions/triggers, speed, turn behaviour, camera settings) — so the whole thing feeds an automated pipeline instead of being redrawn by hand each time.

This report was scoped and re-scoped mid-research by the coordinator; the final scope is the waypoint-mission data model (not just area/grid generation), a judgment on DJI WPML's two-layer `template.kml`/`waylines.wpml` model vs. a tool-neutral intermediate, hand-authored/object-targeted waypoints, and diffability across repeat visits — plus the original Q2 (editing/storage) and Q3 (scalability) questions. A sibling research pass in this same repo, `docs/research/mission-planning-automation-2026.md`, already covers **aircraft-specific limits** — which WPML elements DJI Fly on the Mini 5 Pro actually honours, the USB/MTP delivery mechanism, and the photo-triggering gap — in depth; this report leans on that work rather than re-deriving it, and flags every place its own conclusion depends on those limits.

---

## Recommendation (direct answer)

**Do not adopt DJI WPML's `template.kml`/`waylines.wpml` pair, and do not adopt QGroundControl's `.plan` format, as the business's own source of truth. Define a small, tool-neutral "mission-as-code" schema of our own — GeoJSON geometry plus a thin YAML/JSON parameter layer, validated by a JSON Schema, tracked in Git — and treat every WPML KMZ as a *compiled build artifact*, never hand-edited and never diffed directly.**

Reasoning, in order of weight:

1. **DJI's own two-layer model doesn't survive contact with the consumer app.** The enterprise Cloud API spec frames `template.kml` as declarative intent (a `templateType`, an overlap/GSD/margin, a polygon) that DJI Pilot 2 compiles into concrete `waylines.wpml` points. That separation is real for the Matrice/enterprise line. But the Mini 5 Pro runs DJI Fly, which — per a third-party generator's own device-verified notes — **rebuilds `waylines.wpml` from `template.kml` every time the operator re-saves or cloud-syncs a mission on the controller**, and both files must already carry the same fully-resolved waypoint list or the re-saved mission comes back with points reordered (dronnix-io/FlyPath, `wpml/consumer.py`, citing its own issue #13; this is corroborated independently by `mission-planning-automation-2026.md`'s finding that DJI Fly's own waypoint UI has no concept of a mapping/area template at all — Q3 of that report). So on the one execution target this business actually has, `template.kml` is not "intent that gets compiled" — it is a second copy of the same concrete output. Using that pair as our authoring format would mean hand-maintaining two synchronized copies of a fully-resolved waypoint list, which is strictly worse than authoring the intent once, ourselves, and generating both files from it.
2. **QGC's `.plan` buys little for the cost of adopting it.** It is JSON (easier to review than XML) and has real complex items (Survey, CorridorScan, StructureScan) with a `CameraCalc` block that is a genuinely good camera-parameter vocabulary to *borrow*. But there is no formal, machine-readable JSON Schema for it — the official dev guide itself marks several fields `?` as undocumented even for QGC's own maintainers (`mavlink/qgc-dev-guide`, `plan.md`) — and its per-waypoint action model is MAVLink `MISSION_ITEM` sequence items (e.g. a separate `MAV_CMD_DO_SET_ROI_WPNEXT_OFFSET` item to point a camera, confirmed in `StructureScanComplexItem.cc`), not actions attached to a waypoint the way WPML's `actionGroup` is. Since DJI Fly is the only execution target today and DJI's action vocabulary (`takePhoto`, `gimbalRotate`, `towardPOI`, `startRecord`/`stopRecord`) is richer and better-documented than what would have to be reverse-mapped from raw `MAV_CMD` numbers, adopting `.plan` as the *authoring* format adds a translation layer (`.plan` → WPML) that buys no accuracy or tooling advantage over just authoring closer to WPML's own vocabulary and skipping the middleman.
3. **What's actually worth keeping from both is the vocabulary, not the file format.** Borrow WPML's per-waypoint concepts (height mode: relative-to-start / EGM96 / AGL; heading mode: followWayline / fixed / smoothTransition / towardPOI + a POI point; turn mode; action + actionTrigger with reachPoint/betweenAdjacentPoints/multipleTiming/multipleDistance) and QGC's `CameraCalc` concept (sensor width/height, focal length, front/side overlap → footprint) as the *field names* in our own schema. This is exactly the ponytail-style move: don't invent new vocabulary, don't adopt a whole foreign file format either — take the field names that are already proven and skip the rest.
4. **Diffability requires a small, hand-meaningful input, not a compiled waypoint list.** A flat list of lat/lon/alt points is not reviewable: changing one overlap percentage on a grid regenerates every waypoint's coordinates and index, so a Git diff of a regenerated KMZ is unreadable noise even though the actual change was one number. What *is* diffable is the input — polygon vertices, altitude/GSD, overlap, direction, drone model, and a short list of hand-placed "look-at" waypoints for structures — a few dozen lines of GeoJSON/YAML per site. Commit the compiled KMZ too (for provenance and so a mission can be re-flown byte-for-byte), but review and version the input, not the output.

Concretely: one GeoJSON `FeatureCollection` per Site (polygon = mapping area, optional polygons = no-fly zones, optional points = hand-authored POI/object waypoints with a `properties` bag for heading mode, gimbal pitch, action list), one small YAML sidecar per mission for scalar parameters (altitude/GSD, overlap, pattern type, drone/camera profile reference), one JSON Schema validating both, all in Git. A generator script (a thin wrapper around `drone-flightplan`, extended with the missing patterns below) compiles this into WPML KMZ. This is elaborated in Q1 and Q2 below.

### 1.2 How higher-level patterns compile down to a waypoint list

- **Grid / double grid (cross-hatch):** every tool reduces this to the same geometry problem — lay parallel lines at `line_spacing = footprint_across × (1 − side_overlap)` across the AOI, rotate to a chosen direction, and (for double grid) repeat at 90° and merge. `drone-flightplan`'s `generate_grid_in_aoi` and FlyPath's `generate_flight_grid` both do this in a local projected CRS (Web Mercator or UTM) and reproject back to WGS84 for output — confirmed by reading both directly. DJI's own `mapping2d` template type in `template.kml` does the same thing on the aircraft/DJI Pilot 2 side but is **not exposed in consumer DJI Fly** (per `mission-planning-automation-2026.md`, Q3: no ecosystem tool observed generating DJI's native `mapping2d`/`mapping3d`/`mappingStrip` template types for consumer output; all of them, including FlyPath and drone-flightplan, generate the plain `waypoint` template type with a pre-computed point list instead).
- **Oblique passes:** WPML's own `mapping3d`/oblique template (5 generated routes: 1 nadir + 4 at `inclinedGimbalPitch`) is again an enterprise-only feature per the same corroborating evidence. `drone-flightplan`'s `generate_3d_waypoints` implements the equivalent idea directly at the waypoint level — it emits a forward pass at `gimbal_angle = 45`/`-45` alternating by row and a return pass at the opposite sign, i.e. it hand-builds what DJI's enterprise firmware would otherwise generate on-aircraft.
- **Orbit:** none of the open-source area-mapping tools researched (`drone-flightplan`, FlyPath) implement orbit generation. QGC has no dedicated "Orbit" complex item either in the documented set (Survey/CorridorScan/StructureScan) — the closest analogue is `StructureScan`, which compiles to a ring of `MAV_CMD_NAV_WAYPOINT` items around the structure's flight polygon at one or more altitude "layers," with a `MAV_CMD_DO_SET_ROI_WPNEXT_OFFSET` item inserted to keep the camera pointed at the structure (confirmed directly in `StructureScanComplexItem.cc`, `appendMissionItems()`). Dronelink's "Orbit" component is the most direct consumer-facing analogue (radius, altitude, start location, direction, speed as first-class parameters) but is closed-source. **This is a gap our own generator has to fill**: an orbit is geometrically simple (points on a circle of radius `r` around a POI, each waypoint's heading/gimbal set to `towardPOI`) and maps cleanly onto WPML's own `towardPOI` heading mode plus `waypointPoiPoint` — it does not require any DJI enterprise feature, just per-waypoint heading control, which is present in the WPML spec and (per the sibling report's Q5) in DJI Fly's own consumer waypoint UI too ("Heading: Follow Course, Point of Interest, Custom, or Manual" — the sibling report's finding, not independently re-verified here).
- **Facade:** WPML has a dedicated `facadeWaylineEnable` flag used with a `LinearRing`/`Polygon` whose vertices carry per-vertex height, generating a wall-following flight plane; DroneDeploy's Facade mission type is the closest consumer analogue (structure height, lowest altitude, capture distance as first-class inputs). Neither `drone-flightplan` nor FlyPath implement this.
- **Corridor:** FlyPath's `corridor_planner.py` and QGC's `CorridorScan` complex item both do the same thing — offset a centreline by `± (corridor_width/2 or computed spacing)` to produce parallel passes, then resample along the line at the photo-trigger spacing. FlyPath's docstring is explicit that its corridor output "matches `grid_planner.generate_flight_grid`'s" shape so downstream code doesn't need to special-case it — a reusable-pattern lesson worth keeping in our own generator (one canonical waypoint-list shape regardless of which pattern produced it).

### 1.3 The DJI WPML two-layer model: is it a good fit for our source of truth?

**No — reasoned in full in the Recommendation above.** Restated briefly with the evidence: the enterprise Cloud API documentation frames the pair as declarative-intent (`template.kml`, holding `templateType`, `overlap`, margin, polygon) versus compiled-executable (`waylines.wpml`, holding concrete points). That is a legitimate and well-documented architecture for the aircraft it targets (M300/M350/M30/M3-series, all explicitly listed in every element's "Product Support" column — **the Mini 5 Pro appears in none of them**, confirming the spec at `github.com/dji-sdk/Cloud-API-Doc` is an enterprise/Cloud-API document, not a description of what DJI Fly's consumer waypoint mode implements). On the actual execution target, a third party that reverse-engineered the format directly from a Mini-series device dump found the model breaks down: DJI Fly's own "resave" behaviour treats `template.kml` as the thing it re-derives `waylines.wpml` from, so an externally-authored KMZ must ship both files already fully resolved and byte-consistent, or a routine re-save on the controller scrambles the mission. That is not "intent compiled to executable" — it's two copies of the same executable that must be kept in lockstep by *us*, which is a worse position than authoring intent once in our own format and generating both DJI files fresh every time.

**Recommendation stands:** use a tool-neutral intermediate of our own (GeoJSON + a small parameter sidecar), borrowing WPML's and QGC's field vocabulary, and treat KMZ generation as a one-way compile step, never a round-trip. If a future aircraft on this business's fleet gets genuine MAVLink support (unlikely for a solo <250 g RPAS operation but worth designing for), the same source-of-truth schema can grow a second compiler target (`.plan`/MAVLink mission items) without touching how missions are authored.

### 1.4 Hand-authored and object-targeted waypoints

Every generated-grid tool in this research treats a waypoint as a coordinate the *algorithm* placed. But the corrected scope explicitly includes waypoints a person places by hand — "look at a structure," "orbit this pole," "record video along this path." The vocabulary for this already exists and is shared, in substance, across WPML and QGC/MAVLink, even though the encoding differs:

- **Look at a fixed point while flying past it:** WPML's `waypointHeadingMode = towardPOI` + `waypointPoiPoint` (lat, lon, alt) on any waypoint or waypoint range. QGC/MAVLink's equivalent is a `MAV_CMD_DO_SET_ROI_LOCATION`-family item inserted into the mission sequence ahead of the waypoints it should apply to (confirmed pattern in `StructureScanComplexItem.cc`, generalizable beyond structure scans). The practical difference: WPML attaches the behaviour *to the waypoint*; MAVLink inserts it as *its own item in the sequence*, which is why QGC's own dev guide has no per-waypoint "POI" field to document — it isn't one.
- **Fixed-angle photo of a specific feature:** WPML's `orientedShoot` (successor to the now-deprecated `accurateShoot`) captures at an explicit gimbal pitch/yaw and target-box position, independent of the waypoint's own heading — the right primitive for "photograph this specific window/panel/sign" rather than "look generally toward the structure."
- **Record video along a path:** `startRecord` at one waypoint's `actionGroup`, `stopRecord` at a later one, with heading mode set per-segment (`followWayline` for a flyover, `towardPOI` for an orbiting reveal, `smoothTransition` for a cinematic pan between two fixed yaw angles).
- **Orbit around an object:** not a first-class WPML action, but trivially expressed as N waypoints on a circle with `towardPOI` heading — see §1.2.

For our schema, this means hand-authored waypoints should be modelled as ordinary GeoJSON `Point` features with a `properties` bag carrying `height_mode`, `heading_mode`, `poi` (a `[lon, lat, alt]` triple when relevant), `gimbal_pitch`, and an `actions` list (`take_photo`, `start_record`, `stop_record`, `hover:{seconds}`) — the same shape as a generated grid waypoint, just placed by a human in an editor instead of by an algorithm. This is what keeps the format reviewable: a hand-placed "look at the west wall of the barn" waypoint is two or three lines of GeoJSON properties, diffable and comprehensible on sight, regardless of whether it sits next to 200 machine-generated grid points in the same file.

### 1.5 Reviewability and diffability across repeat visits

Because the compiled WPML output is index-and-coordinate-dense and regenerates in full from even a one-parameter change (e.g., nudging overlap by 5% reflows every line-spacing calculation and therefore every waypoint's coordinates and index), **the compiled KMZ is not the right artifact to diff.** The practice this points to (elaborated with tooling specifics in Q2):

- Version the *inputs* — Site polygon, no-fly zones, hand-authored POI/object waypoints, and the scalar parameter set (altitude/GSD, overlap, direction, drone/camera profile) — as small, human-readable GeoJSON/YAML files in Git.
- Treat the KMZ as a build artifact: regenerate it deterministically from the input on every flight, optionally commit it too for provenance/audit, but review changes by reading the input diff, not the KMZ diff.
- For **repeat visits to the same Site** (a real recurring need per Q3), this also means "fly the identical mission again" is simply "re-run the compiler against the same input" — no separate archival or manual re-creation step, and no risk of subtly different waypoint placement between visits, which matters for change-detection comparisons between orthomosaics/splats taken months apart.

### Basemap horizontal accuracy in Canada

A polygon traced over a misregistered basemap is a misplaced polygon, so this matters directly for whichever editing tool is chosen.

- **Esri World Imagery**: source imagery resolution is commonly 0.5 m/pixel or better, but Esri's own materials are explicit that **accuracy is not a single number** — it varies tile-by-tile depending on which underlying provider and capture date compose that location's mosaic, and the only way to know the accuracy for a specific area is to check that tile's metadata in ArcGIS ([Esri, "Learning more about the World Imagery basemap"](https://www.esri.com/arcgis-blog/products/imagery/imagery/learning-more-about-the-world-imagery-basemap)). **Licence:** Esri's terms grant a right to trace/validate vector edits against World Imagery, but "any and all other uses... remain subject to" the Esri Master Agreement, and standalone commercial use of the tiles outside an ArcGIS Online/Enterprise licence context is not free — this needs to be checked against the business's specific ArcGIS licensing status before relying on it for paid client deliverables (per [community.esri.com](https://community.esri.com/t5/arcgis-location-platform-developers-ques/inquiry-about-world-imagery/td-p/1569266) and the ArcGIS World Imagery "Uses Permitted" page).
- **Google Earth/Maps**: independent, peer-reviewed accuracy studies found wide variance — one study reported a mean horizontal error around 39.7 m RMSE across a global sample, with much better accuracy in more-developed regions (~24 m RMSE) than developing ones (~44 m RMSE), and accuracy improving sharply over time (16.9 m RMSE for circa-2000 imagery down to ~6.1 m RMSE for 2012+ imagery) ([Horizontal Positional Accuracy of Google Earth's High-Resolution Imagery Archive, PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC3791001/)). This is **an order of magnitude worse** than the sub-metre precision a drone survey needs for boundary placement, and it is not a Canada-specific figure — treat it as a general caution, not a number to plan a flight boundary against.
- **Bing/Microsoft aerial imagery**: no independent horizontal-accuracy study was found in this research; Microsoft's own terms restrict use to the Bing Maps/Azure Maps platform (not standalone image extraction) and require attribution per the Bing Maps Terms of Use ([bingmapsportal.com/terms](https://www.bingmapsportal.com/terms)). **Accuracy figure not verified — see "Could not verify."**
- **Provincial/municipal open orthoimagery (Canada)**: this is the better source for boundary tracing precision, because it is captured and controlled specifically for mapping use, not general basemap browsing. Ontario's open orthophotography is distributed as GeoTIFFs at 16–50 cm pixel size, and a specific historical Ontario dataset (Southwestern Ontario Orthophotography Project, 2006) specified a horizontal accuracy requirement of within 45 cm of true position 95% of the time ([Ontario Open Data, "Open Ontario Imagery"](https://data.ontario.ca/dataset/open-ontario-imagery); accuracy figure via search-derived summary of SWOOP documentation, not independently re-verified against the primary spec PDF in this session — treat the *order of magnitude* (tens of centimetres) as reliable, the specific 45 cm figure as attributable to that one historical dataset rather than a province-wide constant). British Columbia publishes a formal Ortho-Image Specification PDF ([gov.bc.ca, 2019 BC Orthoimage Specs](https://www2.gov.bc.ca/assets/gov/data/geographic/digital-imagery/orthophotos/2019_bc_orthoimage_specs.pdf)) built on USGS/ASPRS-derived accuracy classes, but this session's PDF fetch could not extract the specific numeric accuracy class from the document — **flagged in "Could not verify."** The general, well-supported conclusion: government-sourced Canadian orthoimagery is typically decimetre-class and dramatically better than global consumer web-basemap imagery for boundary tracing, and it should be preferred whenever the AOI falls inside a jurisdiction that publishes it.
- **Practical implication for the workflow**: draw or check the Site boundary against the best available *local* orthoimagery (provincial/municipal open data where it exists) rather than trusting Google/Esri/Bing tiles at face value, and always treat the boundary as provisional until the first flight's own orthomosaic exists — at which point re-tracing the boundary against the project's own, known-accurate output (Q2's "refining a boundary once the first orthomosaic exists" scenario) is both easy in a GeoPackage/QGIS workflow and the natural point to correct any basemap-induced offset for future repeat visits.

## Q3 — Scalability patterns

- **Capture profiles/templates per purpose.** The clearest evidence of this pattern is drone-flightplan's and FlyPath's hardcoded, comment-flagged, per-aircraft camera constants — `calculate_parameters.py`'s `VERTICAL_FOV`/`HORIZONTAL_FOV`/`GSD_to_AGL_CONST` are explicitly commented "(For DJI Mini 4 Pro)," and the ground-speed cap of 11.5 m/s is explicitly attributed to "the DJI Mini 4 Pro controller." This is the anti-pattern version of a capture profile — the "profile" exists, but it's baked into the code rather than externalized. The lesson for this business's own schema: define a small per-drone/camera "profile" object (sensor width/height, focal length, FOV, GSD-to-altitude constant, max reliable ground speed, gimbal pitch range) once — QGC's `CameraCalc` is a ready-made field list for this — and reference it by name from each mission, rather than hardcoding it per script. When the fleet grows past one drone model, or DJI revises the Mini line, only the profile changes, not every mission file.
- **Parameter inheritance/overrides.** drone-tm's own data model demonstrates a real two-level inheritance pattern worth copying directly: a `Project` (`ProjectIn` schema) carries site-wide defaults — `gsd_cm_px`, `altitude_from_ground`, `front_overlap`, `side_overlap`, `gimble_angles_degrees`, `is_terrain_follow`, `dem_source` — and individual `Task`s (confirmed via `app/tasks/task_schemas.py` and `task_splitter.py`) inherit those unless a task-level override is present. WPML itself has the identical concept at the waypoint level: nearly every per-waypoint field (`useGlobalHeight`, `useGlobalSpeed`, `useGlobalHeadingParam`, `useGlobalTurnParam`) is a boolean toggle between "use the template/mission default" and "use this waypoint's own value" — the same inheritance idea, one level down. Our own schema should keep both levels: Site-level defaults, waypoint-level overrides, exactly mirroring WPML's own `useGlobal*` pattern (again: borrow the vocabulary, don't re-invent it).
- **Splitting a mission across batteries.** FlyPath ships this as a first-class function, `split_waypoints(waypoints, n_missions)`, which splits a lawnmower grid's waypoint list into `n_missions` contiguous sub-missions and deliberately shares a "seam" waypoint between consecutive sub-missions so the drone resumes exactly where the previous battery left off (confirmed by reading `grid_planner.py` directly). This is a clean, generalizable pattern: split any generated waypoint list on line boundaries, not mid-line, and overlap the seam by one waypoint. Separately, DJI's enterprise-facing GS Pro app supports true in-mission pause/resume "from last stopped point" after a battery swap, sectioning missions over 99 waypoints into auto-resumed groups ([DJI GS Pro FAQ](https://www.dji.com/ground-station-pro/faq), per the sibling report's Q5) — but **this is a GS Pro (enterprise app) behaviour, not confirmed for DJI Fly on the Mini 5 Pro**; the sibling report explicitly flags DJI Fly's own battery-swap/resume behaviour as unconfirmed and recommends planning for a manual re-launch instead. Given that dependency, FlyPath's explicit-seam-waypoint split is the safer design basis for this business today: plan for pre-split missions sized to one battery's flight time, not for an in-app resume feature that isn't confirmed to exist on the actual hardware.
- **Partitioning a large Site into flights.** drone-tm's `task_splitter.py` (a `TaskSplitter` class operating on Shapely polygons, confirmed by reading the source) exists specifically to divide one large Area of Interest into multiple `Task` polygons, each sized to be flown as one mission/one tasking unit — the project-level `task_split_dimension` parameter in `ProjectIn` controls this split. This is the same problem as battery-splitting a single grid but one level up: split the *area* first (by a target task size), then generate a grid per task, then (if needed) battery-split each task's grid. A three-level decomposition — Site → Task (area partition) → battery-leg (waypoint-list partition) — is the scalable structure to adopt, and both levels already have working open-source reference implementations to study or reuse (drone-tm's task splitter for the first, FlyPath's `split_waypoints` for the second).
- **Reusing an identical plan across repeat visits.** Addressed in Q1.5: because the recommended architecture treats the mission as compiled output of a versioned input, "fly the same mission again" is simply re-running the same compiler against the same committed input — byte-identical waypoints every time, which matters for downstream change-detection between visits (comparing orthomosaics or splats taken months apart is only meaningful if the capture geometry didn't drift). This is a property the recommended architecture provides for free; it is not something any of the researched consumer tools (Pix4Dcapture, DroneDeploy, DJI Fly itself) advertise explicitly, though DroneDeploy's "overlay coverage areas of other flight plans" map-settings feature suggests professional planners do value seeing prior flight coverage when planning a repeat visit.
- **Naming/organization.** No formal standard was found for mission/file naming across any tool researched — this appears to be organizational convention, not tooling. The mission-as-code structure implies its own natural convention: one directory per Site (a stable slug, matching the pattern drone-tm's own `ProjectIn.slug` computed field uses — `slugify(name)` — confirmed in `project_schemas.py`), with dated sub-files or Git tags per visit/revision, and the compiled KMZ named to embed the Site slug, visit date, and pattern type for unambiguous identification once it's sitting alone on the RC2's internal storage.
