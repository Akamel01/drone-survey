# Viewing, Editing, and Web Delivery for Orthomosaics, Gaussian Splats, and Meshes — 2026 Findings

Research date: September 2026. Sources are cited inline; where a claim could not be independently confirmed from a primary source, that is flagged explicitly rather than asserted.

---

## Bottom-line recommendation

**Local inspection/editing (on the 8GB M1 MacBook Air, with a Linux/RTX 4070 SUPER box on Tailscale as backup):**

| Deliverable | Local tool | Why |
|---|---|---|
| Gaussian splat cleanup (floaters, cropping, ground noise) | **PlayCanvas SuperSplat Editor** (browser-based, MIT license), run against the Tailscale box's browser or locally for smaller scenes | Purpose-built for exactly this editing workflow — lasso/box/flood/eyedropper selection, invert-and-delete cropping, floater isolation — and is the only tool in this space that both edits and is fully open source ([PlayCanvas Developer Site](https://developer.playcanvas.com/user-manual/supersplat/editor/editing-splats/), [GitHub](https://github.com/playcanvas/supersplat)). For aerial scenes heavy enough to strain 8GB of unified memory, do the cleanup pass on the RTX 4070 SUPER box (remote browser via Tailscale, or `npm run develop` locally there) rather than the MacBook. |
| Point cloud / mesh inspection | **CloudCompare** (GPL-3.0) | Handles up to roughly 120 million points with 2GB of memory and is the de facto tool for manual point-cloud/mesh cleanup and comparison ([GitHub](https://github.com/CloudCompare/CloudCompare)). Runs natively on Apple Silicon. |
| Orthomosaic QA | **QGIS** with the COG loaded directly, or any GDAL-based viewer | Not deeply researched here since it wasn't asked for, but GDAL/QGIS is the standard free path. |

**Web delivery (embedded in the operator's own site, self-hosted, no per-seat licence):**

| Deliverable | Web tool | Why |
|---|---|---|
| Gaussian splat | **PlayCanvas SuperSplat Viewer** (`@playcanvas/supersplat-viewer`, MIT), fed `.sog` files | Same editor's companion viewer compiles to a static, self-hostable site and is designed to be embedded with custom UI; SOG compression (~15–20× smaller than PLY) makes aerial scenes actually streamable ([SuperSplat Viewer docs](https://developer.playcanvas.com/user-manual/supersplat/viewer/), [SOG format spec](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/sog/), [GitHub](https://github.com/playcanvas/supersplat-viewer)). |
| Orthomosaic | **COG + MapLibre GL JS + `maplibre-cog-protocol`** | Serves a Cloud-Optimized GeoTIFF directly from static hosting (S3, Cloudflare R2, or the operator's own server) via HTTP range requests, with zero tile-server backend ([geomatico/maplibre-cog-protocol](https://github.com/geomatico/maplibre-cog-protocol), [geomatico blog](https://geomatico.es/en/serverless-rasters-in-maplibre-the-cog-protocol-extension/)). |
| Mesh / point cloud | **Potree** (BSD-2-Clause) | Runs from a static file host with no server-side component needed beyond a converted Potree octree, and can be embedded via iframe ([Potree GitHub](https://github.com/potree/potree)). |

**There is no single open-source tool that does all three jobs, locally or on the web.** See Question 5 below for the direct answer and evidence. The practical combination is: SuperSplat for splats, CloudCompare/Potree for point clouds and meshes, and COG+MapLibre for orthomosaics — three fit-for-purpose tool stacks, not one platform.

**Emerging risk worth flagging up front:** none of the splat editing/viewing tools researched publish a hard scene-size or RAM ceiling; the practical constraint is Chrome/Safari tab memory and WebGL2/WebGPU buffer limits, not a documented spec. This is the single biggest unknown for the 8GB MacBook Air (see Risks section).

## 1. Gaussian splat viewing and editing (open source, 2025–2026)

### PlayCanvas SuperSplat (Editor)
- **License:** MIT, fully open source ([GitHub](https://github.com/playcanvas/supersplat)).
- **Edits or only views:** Edits. Eight selection tools — Picker, Lasso, Polygon, Brush, Flood, Eyedropper, Sphere, Box — support cropping (select region to keep, invert, delete) and floater removal (isolate via Flood/Lasso in "Rings" mode, then delete); also supports locking finished regions, duplicating/separating selections, and color/opacity retouching ([PlayCanvas editing-splats docs](https://developer.playcanvas.com/user-manual/supersplat/editor/editing-splats/)).
- **Runs where:** Entirely in-browser (superspl.at/editor), nothing to install; can also run locally via Node.js for development ([GitHub](https://github.com/playcanvas/supersplat)).
- **Self-hostable/embeddable:** The Editor itself is a browser tool for the operator's own use, not typically embedded for clients — but its companion **SuperSplat Viewer** package is explicitly designed for self-hosting and embedding (see below).
- **Large-scene handling:** For scenes above roughly 10 million Gaussians, incremental/streamed loading can be enabled to avoid exhausting browser memory; recent engineering work moved to chunked GPU storage rather than keeping full float copies in JavaScript, substantially cutting memory use, and the SOGS/SOG streamed-LOD format is built for progressive loading of 10M+ Gaussian scenes ([WebGPU community writeup](https://www.webgpu.com/showcase/supersplat-3d-gaussian-splat-editor/)). There are also open GitHub issues describing WebGL/WebGPU crashes tied to SOG loading in some configurations, so this is not bulletproof ([GitHub issue #864](https://github.com/playcanvas/supersplat/issues/864)).
- **Formats consumed:** PLY (standard and compressed), binary SPLAT, SOG/SOGS bundles, KSPLAT, CSV, camera-pose and animation files, SuperSplat project files ([Import and Export docs](https://developer.playcanvas.com/user-manual/supersplat/editor/import-export/), corroborated via [DeepWiki supported-formats page](https://deepwiki.com/playcanvas/supersplat/6.2-supported-file-formats)).
- **Formats emitted:** PLY (standard and a Morton-ordered, quantized "compressed PLY" variant), SPLAT, and packaged viewer HTML/ZIP bundles for direct publishing (same sources as above).

### PlayCanvas SuperSplat Viewer
- **License:** MIT ([GitHub](https://github.com/playcanvas/supersplat-viewer)).
- **Edits or only views:** View-only (orbit/pan/zoom, annotations, camera animation playback, optional collision/walk controls, WebXR).
- **Runs where:** Compiles to a self-contained static website; distributed as an npm package (`@playcanvas/supersplat-viewer`) ([GitHub](https://github.com/playcanvas/supersplat-viewer)).
- **Self-hostable/embeddable:** Yes — this is its explicit purpose. It can be hosted on the operator's own infrastructure and embedded with custom surrounding UI via a `renderViewerHtml()` call that takes custom asset URLs and settings ([PlayCanvas Viewer docs](https://developer.playcanvas.com/user-manual/supersplat/viewer/)).
- **Large-scene handling:** Configurable "splat budget," LOD streaming, and both WebGPU and WebGL2 render paths with automatic fallback ([GitHub](https://github.com/playcanvas/supersplat-viewer)); no published hard ceiling was found.
- **Formats consumed:** `.ply`, `.sog`, `.compressed.ply`, `.meta.json`, `.lod-meta.json`, plus `.glb` for collision meshes and equirectangular skyboxes ([GitHub](https://github.com/playcanvas/supersplat-viewer)).

### Nerfstudio viewer (Viser) + gsplat/Splatfacto
- **License:** Apache 2.0, commercially usable ([Radiance Fields](https://radiancefields.com/nerfstudio-1-0-and-splatfacto-released)).
- **Edits or only views:** Primarily a training/inspection viewer, not a cleanup editor. It exposes a scene-crop bounding box (`set_crop`) usable during training/export, but it does not offer SuperSplat-style per-Gaussian lasso/flood selection for floater removal ([nerfstudio viewer_elements source](https://docs.nerf.studio/_modules/nerfstudio/viewer/viewer_elements.html)).
- **Runs where:** The current viewer (Viser, built on Three.js and packaged as a React app at viewer.nerf.studio) connects over a websocket to a training/inference process running on your own machine — i.e., it's a local-network tool, not something designed to be embedded standalone on a client-facing website ([Radiance Fields](https://radiancefields.com/nerfstudio-1-0-and-splatfacto-released)).
- **Export:** Splats export via `ns-export gaussian-splat` to `.ply`; export is only available from trained splat models, not from NeRF (nerfacto) models ([GitHub issue #2732](https://github.com/nerfstudio-project/nerfstudio/issues/2732), [DeepWiki export docs](https://deepwiki.com/nerfstudio-project/nerfstudio/8-exporting-and-evaluation)).
- **Verdict for this use case:** Fine as a training-time sanity check since it's already in the Nerfstudio/splatfacto pipeline, but it is not a substitute for SuperSplat's cleanup workflow, and it's not a web-embeddable client deliverable tool.

### Blender Gaussian Splat addons
Several addons exist, with real differences in licensing and capability:
- **3DGS Render by KIRI Engine:** Free and open source; edits splats using Blender's native selection tools plus modifiers, cropping, and color tools, and supports animating splats by baking motion from a proxy mesh; now moving to community-led maintenance after KIRI's initial development ([80.lv](https://80.lv/articles/animate-gaussian-splats-in-blender-using-3dgs-render-5-0), [GitHub](https://github.com/Kiri-Innovation/3dgs-render-blender-addon)).
- **SplatForge:** **Not open source** — a $49 paid Blender addon. Handles 100M+ splats and real-time Eevee rendering, with culling, densification, pruning, slicing, opacity adjustment, and color grading ([thefuture3d.com review](https://www.thefuture3d.com/software/splatforge/)). Flagged separately because it fails the "no per-seat commercial licence" constraint, though its capability profile (very large scene handling) is relevant if the operator ever reconsiders.
- **BlendSplat:** A node-based asset library for splats in Blender; license/openness not confirmed from available sources — **could not verify**.
- **SkySplat:** Described as an open-source project for 3DGS in Blender; specific license and feature depth not verified beyond the project's own description ([skysplat.org](https://skysplat.org/)) — **could not verify licence terms**.

Given the open-source constraint, **3DGS Render by KIRI Engine** is the only credible Blender option; it is a secondary/animation-oriented tool rather than a primary cleanup tool, and SuperSplat remains the stronger fit for pure crop/floater work.

### Spark (Three.js, by World Labs)
- **License:** MIT, open source, actively developed as of 2026 (unlike mkkellogg's GaussianSplats3D, which its own author says is no longer actively maintained and recommends Spark as the successor) ([GitHub GaussianSplats3D README](https://github.com/mkkellogg/GaussianSplats3D/blob/main/README.md), [GitHub sparkjsdev/spark](https://github.com/sparkjsdev/spark)).
- **Edits or only views:** Primarily a rendering/viewer library, but documentation describes "real-time editing" support and a shader-graph system for GPU-based splat generation — depth of editing tooling relative to SuperSplat's dedicated UI was not independently verified — **could not fully verify editing feature parity**.
- **Runs where:** In-browser, Three.js-based.
- **Self-hostable/embeddable:** Yes, designed for embedding via CDN import maps or bundling into your own Three.js app.
- **Formats:** PLY (including compressed), SPZ, SPLAT, KSPLAT, SOG — the broadest format support of any renderer found in this research ([GitHub](https://github.com/sparkjsdev/spark)).
- **Large-scene handling:** Targets "98%+ WebGL2 support" and claims fast rendering on low-powered mobile devices, with correct multi-object depth sorting; no published hard scene-size ceiling found.

### mkkellogg/GaussianSplats3D
- **License:** Open source (repository does not headline a specific SPDX license in the sources reviewed — **could not fully verify exact license text**), but per the maintainer's own README, the project is no longer in active development and Spark is recommended instead ([GitHub README](https://github.com/mkkellogg/GaussianSplats3D/blob/main/README.md)). Notable mainly as the origin of the **.ksplat** format (chunked, depth-sorted, progressive-streaming design that shows a recognizable scene within 0.5–1 second even for 100MB+ files) ([Polyvia3D KSPLAT explainer](https://www.polyvia3d.com/formats/ksplat)).

### What's newest for 2025–2026
- **SOG (Spatially Ordered Gaussians):** PlayCanvas's successor to SOGS, launched roughly September 2025; a compact container using quantized, WebP-encoded attribute images, achieving ~15–20× smaller files than PLY (one cited example: a 1GB PLY compressed to 42MB) ([PlayCanvas SOG format docs](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/sog/), [PlayCanvas blog](https://blog.playcanvas.com/playcanvas-open-sources-sog-format-for-gaussian-splatting/)).
- **SPZ / SPZ 4:** Niantic Spatial's ZSTD-compressed splat format (MIT license), roughly 10× smaller than PLY; SPZ 4 (2026) is 3–5× faster to compress and 1.5–2× faster to load than prior versions, and is now referenced in Khronos's compression extension for glTF ([Auganix](https://www.auganix.org/xr-news-niantic-spz-4-gaussian-splats/), [Open Source For You](https://www.opensourceforu.com/2026/05/niantic-spatial-open-sources-spz-4-to-scale-gaussian-splats-across-xr-robotics-and-web-workflows/), [GitHub license](https://github.com/nianticlabs/spz/blob/main/LICENSE)).
- **KHR_gaussian_splatting (glTF extension):** Khronos published a release candidate in February 2026 with ratification expected Q2 2026, backed by Autodesk, Bentley Systems, Huawei, Niantic Spatial, and Nvidia; a companion `KHR_gaussian_splatting_compression_spz` extension formalizes SPZ as the standard compressed payload ([Khronos press release](https://www.khronos.org/news/press/gltf-gaussian-splatting-press-release), [CG Channel](https://www.cgchannel.com/2026/02/3d-gaussian-splats-are-being-added-to-the-gltf-standard/), [Babylon.js radiancefields coverage](https://radiancefields.com/babylon.js-v9.0-3dgs-gets-shadows-sogs-and-triangle-splatting-support-announced)). **Note:** as of this research date (September 2026), I could not independently confirm final ratification status beyond "expected Q2 2026" — treat as recent/likely-finalized but verify current status before depending on it.
- **Cesium / 3D Tiles for geospatial splats:** Cesium shipped KHR_gaussian_splatting support in CesiumJS 1.139 and Cesium for Unreal v2.23.0 in March 2026, using 3D Tiles as the spatial index with hierarchical LOD so splat datasets can stream from city scale to sub-centimeter detail without loading the full reconstruction ([Radiance Fields](https://radiancefields.com/cesium-brings-khr_gaussian_splatting-support-to-cesiumjs-and-unreal-engine), [Cesium blog](https://cesium.com/blog/2026/04/27/3d-gaussian-splats-lod/)). This is directly relevant to a georeferenced aerial-survey business since it's the only pipeline researched here that natively ties splats to geospatial LOD streaming — CesiumJS itself is open source (Apache 2.0), though this was not independently re-verified in this pass — **could not fully verify CesiumJS's current license terms from a primary source in this research round.**

## 2. Splat web embedding standard, 2026

There is no single dominant proprietary embed widget the way, say, YouTube is for video — the "standard" is a small set of open-source WebGL/WebGPU renderers plus a converging set of compressed formats.

- **PlayCanvas Engine + SuperSplat Viewer:** MIT-licensed; PlayCanvas is described as leading specifically in Gaussian splat rendering quality among the web engines, with compute-based splat rendering, though it remains WebGL2-first with WebGPU still maturing as a default path ([Cinevva 2026 comparison](https://app.cinevva.com/blog/2026-06-09-web-game-engines-2026-comparison)). Bundle size sits around 1–2MB for the full engine ([Cinevva bundle comparison](https://app.cinevva.com/guides/web-game-engines-comparison)).
- **Three.js + Spark:** Three.js itself is roughly 168KB gzipped, the lightest of the three engines compared, and Spark builds splat rendering on top of it under an MIT license ([utsubo.com comparison](https://www.utsubo.com/blog/threejs-vs-babylonjs-vs-playcanvas-comparison), [GitHub sparkjsdev/spark](https://github.com/sparkjsdev/spark)).
- **Babylon.js:** Apache 2.0, roughly 1.4MB initial bundle (smaller when targeting WebGPU with WGSL-native shaders in the 8.0 cycle); has native, unified loading for `.splat`, `.ply`, `.spz`, and `.sog` ([Windows Developer Blog on Babylon 8.0](https://blogs.windows.com/windowsdeveloper/2025/03/31/part-2-babylon-js-8-0-audio-gaussian-splat-and-physics-updates/), [Radiance Fields on Babylon 9.0](https://radiancefields.com/babylon.js-v9.0-3dgs-gets-shadows-sogs-and-triangle-splatting-support-announced)).
- **Mobile/browser support:** Safari added WebGPU support across macOS, iPadOS, iOS, and visionOS starting with Safari 26 (September 2025), with the iOS/iPadOS rollout landing in Safari 18.2 in early 2026; as of mid-2026, WebGPU is estimated to cover roughly 70% of active mobile devices globally, so a WebGL2 fallback is still necessary for full reach ([DEV Community on WWDC 2025 WebGPU](https://dev.to/arshtechpro/wwdc-2025-webgpu-on-apple-platforms-16pa), [webo360solutions WebGPU browser support 2026](https://webo360solutions.com/blog/webgpu-browser-support/)). All three engines/renderers above ship WebGL2 fallbacks, which matters directly for the operator's likely client base viewing on phones.

**Emerging standard compressed format:** SOG and SPZ are the two real contenders, and they are converging rather than competing — SPZ is now the format Khronos names in its glTF compression extension, while SOG is PlayCanvas's own high-ratio format for its ecosystem. Compression ratios: **SPZ ≈ 10× smaller than PLY** ([Windows Developer Blog](https://blogs.windows.com/windowsdeveloper/2025/03/31/part-2-babylon-js-8-0-audio-gaussian-splat-and-physics-updates/)); **SOG ≈ 15–20× smaller than PLY**, with one documented example shrinking a 1GB PLY to 42MB ([PlayCanvas SOG docs](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/sog/)). For an aerial-survey operator, SOG is the more relevant choice today because it has direct, first-party support in the SuperSplat Editor/Viewer pipeline already recommended above; SPZ is worth tracking because of its glTF standardization path.

**Realistic streaming scale:** No renderer in this research published a hard "safe scene size" number for web delivery. The qualitative pattern across sources is: a few million Gaussians (tens of MB compressed) streams comfortably on mobile; tens of millions of Gaussians benefits materially from LOD/streaming systems like SuperSplat Viewer's splat budget or Cesium's hierarchical 3D Tiles LOD; a full-resolution aerial capture in the hundred-million-Gaussian range (as seen in research reconstructions, see Question 5's risk notes) is not something any of these web viewers were shown handling directly — it would need to be reduced/leveled first. **Could not verify a specific number of Gaussians "safe" for average client hardware from a primary source.**

## 3. Orthomosaic web delivery, 2026

- **Cloud-Optimized GeoTIFF (COG)** is the standard container: an internally tiled, overview-pyramided GeoTIFF that supports HTTP range requests so a client only fetches the bytes it needs ([cogeo.org](https://cogeo.org/)).
- **Static hosting without a tile server is possible today.** `maplibre-cog-protocol` (MIT license) is a MapLibre GL JS plugin that renders COGs directly in the browser by issuing HTTP range requests against the file, with no backend tiler; one cited example handles a 12GB digital elevation model at 2m/pixel resolution this way ([geomatico/maplibre-cog-protocol GitHub](https://github.com/geomatico/maplibre-cog-protocol), [geomatico blog](https://geomatico.es/en/serverless-rasters-in-maplibre-the-cog-protocol-extension/)). A February 2026 plugin, `maplibre-gl-components`, extends this pattern to also support Zarr, PMTiles, FlatGeobuf, GeoParquet, and STAC catalogs from static storage ([gishub.org](https://gishub.org/blog/maplibre-gl-components/)).
- **Server-based tiling remains an option** via TiTiler (a Python service that renders COG tiles on the fly, usable as a serverless Lambda tiler via rio-tiler) for cases where a backend is acceptable, but it is not required for the "embed on my own static site" constraint ([search summary citing TiTiler/rio-tiler](https://cogeotiff.github.io/rio-cogeo/CLI/)).
- **Client libraries:** MapLibre GL JS is the library with the most direct, actively maintained COG-in-browser plugin support found in this research (both `maplibre-cog-protocol` and `maplibre-gl-raster`); Leaflet and OpenLayers were not found to have an equivalently mature, actively maintained no-backend COG plugin in the sources reviewed — **could not verify a comparably capable, current Leaflet/OpenLayers COG-without-server plugin**, so MapLibre GL JS is the safer default recommendation for this use case.
- **What to generate at export time:**
  - Enable ODM's native COG export flag: `--cog` (WebODM in fact forces this on internally for its own dynamic tiler regardless of the UI toggle) ([ODM community forum](https://community.opendronemap.org/t/can-not-disable-cog-option-cloud-optimized-geotiffs-in-webodm/8184/2), [ODM docs](https://docs.opendronemap.org/arguments/cog/)).
  - If converting an existing GeoTIFF after the fact: `gdal_translate -of COG -co COMPRESS=JPEG -co QUALITY=85 input.tif output_cog.tif`, or use the `rio cogeo create` CLI, which supports `--overview-level` and `--overview-resampling` (nearest, bilinear, cubic, cubic_spline, lanczos, average, mode, gauss) ([rio-cogeo CLI docs](https://cogeotiff.github.io/rio-cogeo/CLI/)).
  - To add overview pyramids manually: `gdaladdo -r average /path/to/image.tif 2 4 8 16 32 64 128 256 512 1024`; guidance seen in sources recommends building overviews locally after download rather than baking them in pre-transfer to avoid inflating the file you're moving around first ([Heritage GIS](https://www.archaeological-heritage-gis.org/photogrammetry-3d-site-mapping-pipelines/orthomosaic-generation-and-tiling/generating-cloud-optimized-geotiff-orthomosaics/)).
- **Practical size limits:** Not quantified with a hard number in any source reviewed; the architecture (range-request-based tiling) is explicitly designed to decouple "file size" from "what the browser must download," so the practical limit is more about the origin server/CDN supporting HTTP range requests reliably than about GB size per se. **Could not verify a specific maximum COG size for browser delivery.**

## 4. Mesh and point-cloud viewing

- **CloudCompare** (GPL-3.0, per its GitHub license file — note this is copyleft, meaning modifications you distribute must also be open-sourced, though using it as-is for internal QA carries no such obligation): the standard free desktop tool for point-cloud and mesh inspection, comparison, and manual cleanup, handling "more than 10 million points, and up to 120 million with 2GB of memory" ([GitHub](https://github.com/CloudCompare/CloudCompare)). Stable release as of mid-2026 is in the 2.13.x line with GPU-accelerated rendering ([search-derived summary, thefuture3d.com](https://www.thefuture3d.com/blog/best-point-cloud-software-2026/)) — **could not independently verify the exact current version number from CloudCompare's own release page in this pass.** It is directly used in ODM community workflows to manually edit point clouds ([ODM community forum](https://community.opendronemap.org/t/edited-point-cloud-with-cloudcompare-wont-rerun-from-odm-meshing/21449)).
- **Blender:** widely used for mesh inspection/retouching of ODM textured meshes via standard OBJ/glTF import; not a dedicated point-cloud tool.
- **Potree** (BSD-2-Clause license, confirmed from the repository's own LICENSE file): the standard open-source WebGL point-cloud viewer for large datasets, built to run from plain static hosting — "simply upload the Potree folder... to a web server. It is not required to install node.js on your webserver" — and it supports iframe embedding into third-party pages ([GitHub](https://github.com/potree/potree), [LICENSE](https://raw.githubusercontent.com/potree/potree/develop/LICENSE)). It requires converting LAS/LAZ/EPT point clouds into Potree's own octree format via PotreeConverter first, not raw ODM output directly.
- **What changed in 2025–2026:** the search results point mainly to routine maintenance (e.g., third-party Potree2-based plugins in NVIDIA Omniverse receiving point updates into 2026) rather than a major architectural shift — no primary Potree changelog confirming a specific headline release in this window was located, so this should be treated as unconfirmed. The more significant 2025–2026 development in this whole space is not to point-cloud viewers themselves but to Gaussian splats absorbing some of the point-cloud/mesh use case via Cesium's 3D Tiles + KHR_gaussian_splatting pipeline (see Question 5), which increasingly treats splats, meshes, and point clouds as sibling tile types in one geospatial delivery format ([Cesium blog](https://cesium.com/blog/2026/04/27/3d-gaussian-splats-lod/)).

## 5. The unification question

**Direct answer: no, there is no single open-source tool in 2026 that credibly handles all three deliverable types (georeferenced raster, Gaussian splat, mesh/point cloud) for both local inspection and web embedding.** Practitioners use fit-for-purpose tools per data type, stitched together. Evidence:

- SuperSplat (Editor + Viewer) only handles Gaussian splats — its own documentation and format list never mention GeoTIFF or LAS/LAZ point-cloud ingestion ([PlayCanvas developer docs](https://developer.playcanvas.com/user-manual/supersplat/)).
- CloudCompare and Potree only handle point clouds and meshes; neither tool's documentation mentions native Gaussian splat rendering or GeoTIFF raster serving ([CloudCompare GitHub](https://github.com/CloudCompare/CloudCompare), [Potree GitHub](https://github.com/potree/potree)).
- MapLibre/COG tooling only handles 2D georeferenced rasters; it has no 3D splat or mesh rendering capability.
- The closest thing to a unifying *platform* found in this research is **Swyvl**, which explicitly organizes splats, point clouds (via an embedded Potree instance), orthomosaics (on a map), and reports under one branded client-facing link ([swyvl.io](https://swyvl.io/blog/best-gaussian-splat-viewers/)). However, **Swyvl is a commercial hosted SaaS, not open source** — its own materials describe it as a service with branded share links and paid delivery/storage tiers, which fails this operator's "no third-party hosting, no per-seat licence" constraint. It is flagged here separately per your instructions rather than recommended: worth knowing it exists as a benchmark for what an integrated experience looks like, and worth revisiting if the operator ever decides self-hosting three separate tools is more overhead than a subscription is worth. **Exact Swyvl pricing could not be confirmed** — the pricing page was referenced but its figures were not retrieved in this research pass.
- On the commercial-but-not-open-source processing side, PIX4Dmatic already generates both a Gaussian splat and a dense point cloud from a single run, and Metashape, Pix4D, and DroneDeploy are all reported as moving toward shipping native 3DGS support by the end of 2026 ([support.pix4d.com](https://support.pix4d.com/hc/gaussian-splatting-pix4dmatic), [thefuture3d.com state-of-3DGS article](https://www.thefuture3d.com/blog/state-of-gaussian-splatting-2026/)) — this is evidence the *industry* is converging on splats as a standard deliverable, not evidence that any single *open-source* tool spans all three data types end to end.
- The nearest technical convergence point is Cesium/3D Tiles, which is explicitly designed to hold meshes, point clouds, and (as of 2026) Gaussian splats as sibling tile types in one geospatial streaming format, with CesiumJS as the shared web viewer ([Cesium blog](https://cesium.com/blog/2026/04/27/3d-gaussian-splats-lod/)). This is the closest thing to "one web viewer, multiple data types" found in this research, but it does not include orthomosaic-as-2D-raster-map delivery or local desktop editing/cleanup in the same tool, so it doesn't fully satisfy the unification bar either.

**Conventional combination, confirmed across the sources above:** SuperSplat (splat cleanup + splat web delivery) + CloudCompare (point-cloud/mesh desktop cleanup) + Potree (point-cloud web delivery) + COG/MapLibre (orthomosaic web delivery), glued together by the operator's own website shell.

## 6. Timelapse / multi-date presentation

**For orthomosaic maps:** Purpose-built open-source swipe/compare tooling exists and is mature:
- `maplibre-gl-compare` (official MapLibre plugin, migrated from the original Mapbox GL compare plugin after Mapbox's license change) provides a synced-pan slider between two MapLibre map instances, vertical or horizontal ([GitHub](https://github.com/maplibre/maplibre-gl-compare)).
- `maplibre-gl-swipe` and `leaflet-side-by-side` provide equivalent draggable-slider comparison controls for MapLibre and Leaflet respectively ([opengeos/maplibre-gl-swipe](https://github.com/opengeos/maplibre-gl-swipe), [leaflet-side-by-side](https://github.com/TimP4w/leaflet-side-by-side)).
- For simpler flat-image before/after comparisons (not full interactive maps), **JuxtaposeJS** from Northwestern's Knight Lab is a free, open-source before/after slider that needs only two image URLs ([GitHub](https://github.com/NUKnightLab/juxtapose)).
- On the data-prep side, WebODM added an "Auto Alignment" feature specifically so orthomosaics from different survey dates line up accurately for comparison, building on ODM's existing `--align` flag (which aligns a new reconstruction to a prior point cloud or single-band DEM supplied as `align.laz`/`align.las`/`align.tif`) ([WebODM community forum](https://community.opendronemap.org/t/the-new-auto-alignment-feature-is-a-game-changer/23787), [ODM align docs](https://docs.opendronemap.org/arguments/align/)). ODM also ships a `contrib/time-sift` script implementing Time-SIFT, a method for multi-temporal analysis without needing to co-register the data first ([ODM community forum](https://community.opendronemap.org/t/how-to-implement-change-detection/3821)).

**For 3D (splats/point clouds):** Nothing purpose-built and production-ready was found. The closest thing is **SplatAlign**, a research-grade open-source tool that performs ICP alignment between two 3DGS captures of the same site at different times and supports a "time-toggle" viewer to switch between temporal states from the same camera position, citing roughly 5cm alignment accuracy with ground filtering to exclude seasonal vegetation noise ([GitHub](https://github.com/terminusfilms/splatalign)). This reads as an emerging/research tool rather than a mature, widely adopted product — treat it as a starting point to prototype from, not a drop-in solution. Beyond that, the pattern in the broader 3DGS research literature (Spacetime Gaussian Splatting, Cross-Temporal 3DGS, etc.) is squarely academic/dynamic-scene-focused rather than aimed at the "same static site, five site visits a year" use case an aerial-survey operator actually has ([arXiv: Spacetime Gaussian Splatting](https://openaccess.thecvf.com/content/CVPR2024/papers/Li_Spacetime_Gaussian_Feature_Splatting_for_Real-Time_Dynamic_View_Synthesis_CVPR_2024_paper.pdf), [arXiv: Cross-Temporal 3DGS](https://arxiv.org/html/2512.00534)).

**What people improvise with, based on the evidence above:** align each date's splat/point cloud independently (ICP or manual alignment in CloudCompare), then build a custom front-end control that swaps between multiple pre-aligned SuperSplat Viewer or Potree instances loaded at the same camera pose — essentially a bespoke version of what JuxtaposeJS/maplibre-gl-compare do for 2D, hand-rolled for 3D because no equivalent shipped library was found. This is a real engineering task, not a checkbox feature, and should be scoped as custom development rather than "install a plugin."

## Biggest risks / what would make this fail

1. **8GB M1 MacBook Air memory ceiling is real and undocumented for these tools.** None of SuperSplat, Spark, or Babylon.js publish a hard "safe" Gaussian count or file size for a given RAM budget — the only concrete data point found is that a 10-million-Gaussian scene needs under 5GB of VRAM just to *render* ([research-derived figure](https://arxiv.org/html/2507.01110v3)), and that's before accounting for browser/OS/tab overhead on a shared 8GB unified-memory system with no dedicated VRAM at all. A full-resolution aerial capture at tens to hundreds of millions of Gaussians (the scale cited in aerial reconstruction research: 145 million Gaussians for a 13 km² capture) is very plausibly beyond what an 8GB Air can open at all, even with SOG/streamed-LOD loading, since streaming reduces bandwidth but still needs working memory for what's currently in view ([arXiv aerial reconstruction example](https://www.spheron.network/blog/deploy-3d-gaussian-splatting-gpu-cloud/)). **Practical mitigation:** do heavy cleanup passes on the RTX 4070 SUPER box over Tailscale (run SuperSplat's dev server there, access via remote browser or remote desktop), and only do final light QA on the Air with an already-downsampled/SOG-compressed scene. This should be treated as a workflow requirement, not an edge case — plan for it explicitly rather than discovering it on a live project.
2. **No open-source multi-date 3D comparison tool is production-ready.** SplatAlign is research-grade. Building the "3D timelapse" deliverable will require real engineering effort (custom camera-pose syncing across independently-aligned SuperSplat Viewer instances), not off-the-shelf integration — this is a project cost that should be budgeted, not assumed to be a weekend plugin install.
3. **Format fragmentation is still active.** SOG, SPZ, PLY, SPLAT, and KSPLAT are all in live use, and the glTF standardization (KHR_gaussian_splatting) was only at release-candidate stage as of February 2026 with ratification "expected" but not confirmed finalized as of this research. Betting the whole delivery pipeline on one format today risks a rework once the standard lands — SOG is the safest near-term bet given first-party SuperSplat support, but this should be revisited once KHR_gaussian_splatting ratification status is confirmed.
4. **No mature no-server COG plugin confirmed for Leaflet or OpenLayers.** If the operator's website ends up needing Leaflet or OpenLayers for other reasons (rather than MapLibre), the "no tile server" claim in Question 3 may not transfer — this should be checked against the actual site framework before committing.
5. **CloudCompare's GPL-3.0 license is copyleft**, unlike the MIT/Apache/BSD licenses on every other recommended tool. This is not a problem for internal QA use, but if the operator ever redistributes a modified CloudCompare build (rather than just outputs produced with it) as part of a product, GPL obligations would attach. Worth a one-line mental flag, not a blocker for the current use case.
6. **Swyvl and similar hosted platforms are the "give up and pay" fallback** if the DIY stack proves too much integration overhead for a solo operator — flagged per your instructions, but its exact pricing was not confirmed in this research and should be checked directly before treating it as a real fallback option.
