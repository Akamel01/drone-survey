# Free-of-Charge Photogrammetry Engines for a Commercial Aerial-Survey Pipeline — 2026

Prepared September 2026. Scope: the operator is no longer fixated on open source — any software that is free of charge (or effectively free at solo-operator revenue) and produces enterprise-grade, georeferenced orthomosaics is in scope, provided it fits a CLI-first, automated pipeline. Paying thousands of dollars remains out of the question. This report supersedes nothing in the existing `orthomosaic-open-source-2026.md` research; it re-evaluates the orthomosaic engine choice against a wider field, above all RealityCapture/RealityScan, now that "free" is the only hard constraint rather than "open source."

---

## Bottom line

**Keep OpenDroneMap (ODM) as the orthomosaic engine. Do not move the automated pipeline to RealityCapture/RealityScan.**

RealityCapture (rebranded RealityScan by Epic Games in mid-2025) is genuinely free below $1M/year gross revenue, has a real CLI with documented orthomosaic and ground-control-point commands, and by reputation produces excellent geometry and textures faster than most competitors. On paper it clears the "free and enterprise-grade" bar this research was asked to re-test. But its Linux story — the only story that matters for this operator's headless, Docker-adjacent Ubuntu box — is a command-line build that Epic's own documentation labels **experimental**, runs the Windows binary under a bundled Wine layer, requires a newer Linux kernel (6.14+) than Ubuntu 24.04 LTS ships by default, and has at least one secondary report of authentication dialogs hanging in true headless environments. None of that is disqualifying in isolation, but stacked together it is meaningfully more operational risk than ODM, which runs natively on Linux, ships official Docker images, and already has a documented, scriptable API surface (NodeODM/PyODM/CloudODM) that this operator has already built a plan around.

The case for switching would need RealityCapture to solve a problem ODM actually has. It doesn't. ODM's known weaknesses — thin structures, water, dense vegetation, low-overlap datasets — are fixed primarily by better flight planning (which the prior research already identified as the real lever), not by a different reconstruction engine. Meanwhile RealityCapture's headline strength, "sharp geometry, excellent textures" and best-in-class mesh output, is a 3D-reconstruction advantage that mostly duplicates ground already covered by the operator's separate, already-committed choice of splatfacto (Apache 2.0) for the gaussian-splatting side of the pipeline — it is not an orthomosaic-quality advantage per se, and orthomosaic generation is explicitly secondary to RealityCapture's 3D-modeling focus.

The one place RealityCapture is worth actually having installed: as a manual, occasional cross-check tool run on a normal Windows machine (or the dual-boot Windows partition, booted deliberately, off the automated critical path) for a specific hard job where ODM's output looks wrong and a second engine's opinion is worth the friction. That is a "keep in the toolbox," not a "rebuild the pipeline around it," conclusion.

## Findings by question

### 1. RealityCapture / RealityScan in depth

**Licensing and the $1M threshold.** RealityScan is free of charge for hobbyists, students, educators, and any individual or company with gross annual revenue under $1,000,000 USD; above that threshold, a paid subscription is required. Secondary sources converge on a per-seat annual price in the neighborhood of $1,250 (roughly €1,379 including regional pricing) once the threshold is crossed. I was not able to load the primary licensing page directly — `realityscan.com/license` redirects through an Epic Games account/login wall that a non-interactive fetch cannot pass — so the exact revenue-threshold and pricing figures here rest on two independent secondary sources (CG Channel's coverage of RealityScan 2.0/2.1/2.2, and aggregation sites) rather than the primary EULA text. I could not confirm whether the free tier carries any attribution requirement or restriction on selling client deliverables produced with it; nothing in the sources I could reach mentions such a restriction, but that is an absence of evidence, not confirmation of its absence. [CG Channel: Epic Games to rebrand RealityCapture as RealityScan 2.0](https://www.cgchannel.com/2025/06/epic-games-to-rebrand-realitycapture-as-realityscan-2-0/) · [CG Channel: RealityScan 2.1](https://www.cgchannel.com/2025/11/epic-games-releases-realityscan-2-1/) · [CG Channel: RealityScan 2.2 adds AMD GPU support](https://www.cgchannel.com/2026/06/epic-games-releases-realityscan-2-2-with-amd-gpu-support/)

**Has Epic changed terms since acquisition?** Yes, twice in visible ways: the June 2025 rebrand from RealityCapture to RealityScan (unifying the desktop app with Epic's separate RealityScan mobile app under one name), and the introduction of AMD GPU support in the 2.2 release (June 2026), which so far is Windows-only. The free-below-$1M / paid-above-$1M structure itself appears unchanged since Epic's original 2021 acquisition of Capturing Reality, based on everything found in this research; I found no report of the threshold or terms shifting.

**Does it run on Linux natively in 2026?** No. The desktop GUI is Windows-only (Windows 10+ and Windows Server 2016+). What exists for Linux is a separate **CLI-only build** that Epic's own documentation explicitly and repeatedly calls **experimental**: it bundles an isolated Wine environment rather than running natively, targets Ubuntu 24.04 (kernel 6.14+) or Fedora 39 (kernel 6.10+), and warns that "editing or modifying files within the bundled Wine prefix is not recommended... at your own risk, as it may cause the installation to break or lead to unstable behavior." A GUI can technically be launched inside that Wine layer for troubleshooting, but Epic's documentation says the UI is "not recommended" there due to graphical glitches, focus issues, and unsupported HTML dialogs, and that the supported production path is CLI-only. One independent practitioner (a working photogrammetrist, not a marketing source) corroborates that the headless CLI itself runs reconstruction pipelines "without issues," while the GUI on Linux "has plenty of problems" — a useful, if single-source, sanity check that the CLI path is more solid than the "experimental" label alone suggests. Separately, note that Ubuntu 24.04 LTS's default GA kernel is older than 6.14; hitting the stated minimum would likely require the HWE kernel stack or a manual kernel bump, which is exactly the kind of extra moving part that complicates a host that also runs a 40-container production Docker stack. [Epic dev docs: RealityScan for Linux](https://dev.epicgames.com/documentation/realityscan/realityscan-for-linux?lang=en-US) · [Epic dev docs: Installation (Linux)](https://dev.epicgames.com/documentation/realityscan/installation-linux) · [Peter Falkingham: RealityScan 2.2 brings AMD GPU support (to Windows)](https://peterfalkingham.com/2026/06/25/realityscan-2-2-finally-brings-amd-gpu-support-to-windows/) · [CG Channel: RealityScan 2.2](https://www.cgchannel.com/2026/06/epic-games-releases-realityscan-2-2-with-amd-gpu-support/)

**Does it have a real CLI suitable for automation, and what can it do headlessly?** Yes, and it is more capable than a bare-bones batch wrapper. RealityScan's documented CLI commands cover the full pipeline end to end: image import, alignment, dense/mesh reconstruction, texturing, and — directly relevant here — **orthomosaic generation and georeferencing**: `calculateOrthoProjection` and `exportOrthoProjection` for producing and exporting orthophotos/DSM/DTM from parameter files, `importGroundControlPoints`/`exportGroundControlPoints` and `importControlPointsMeasurements` for GCP-based registration, and `setProjectCoordinateSystem`/`setOutputCoordinateSystem` for defining the target CRS. A `-headless` flag suppresses the UI, and for true out-of-process automation Epic also documents a **Remote Command Plugin** that exposes RealityScan as a gRPC/REST API rather than requiring shell-level invocation at all. The one caveat worth flagging (single secondary source, not corroborated in the official docs I could reach) is a claim that licence/authentication dialogs can attempt to open even under `-headless` and hang in a genuinely display-less environment — if true, this would need to be solved with a virtual display (Xvfb) or the Remote Command Plugin rather than assumed away. [RealityScan Help: List of All CLI Commands](https://rshelp.capturingreality.com/en-US/appbasics/allcommands.htm) · [RealityScan Help: Command Line Interface](https://rshelp.capturingreality.com/en-US/tutorials/commandline.htm) · [Epic dev community: CLI operations tutorial](https://dev.epicgames.com/community/learning/tutorials/GXlx/realityscan-command-line-interface-cli-operations-in-realitycapture) · [Aerocartwright: Photogrammetry on Linux (secondary source, unverified headless-dialog claim)](https://aerocartwright.com/library/photogrammetry-linux-compared/)

**Does it produce georeferenced orthomosaics, and how mature is that workflow?** Yes, ortho-mosaicking has been a supported feature since the RealityCapture 1.2 "Tarasque" release, and the CLI commands above show it is fully scriptable including GCP-based georeferencing. That said, multiple independent sources — including a direct head-to-head write-up — describe orthomosaic export as secondary to RealityCapture's core 3D-modeling/mesh focus, in contrast to ODM, Pix4D, and Metashape, which are built mapping-first. This doesn't mean the ortho output is bad; it means the feature has had comparatively less dedicated engineering attention and a thinner base of mapping-specific practitioner documentation than tools built around orthomosaics as the primary deliverable. [Aerocartwright: WebODM vs Pix4D vs Metashape vs RealityCapture](https://aerocartwright.com/library/pix4d-vs-metashape-vs-webodm-vs-realitycapture/)

**GPU/CPU/RAM needs, and is the RTX 4070 SUPER (12GB) adequate?** Yes, comfortably on paper. Official Linux-build documentation states an NVIDIA GPU is mandatory (CUDA is required; there is no CPU-only path) with a minimum of 8GB VRAM recommended, and 16GB+ system RAM. The 4070 SUPER's 12GB VRAM clears that floor with headroom, and multiple hardware-guide sources independently describe the 4070 SUPER as suitable for small-to-medium reconstruction projects, with a 4080/4070 Ti recommended only for larger jobs. I could not find a current, official, RealityScan-branded disk-space specification — Epic's own site does not appear to publish updated system requirements post-rebrand, and the historical RealityCapture spec page is gone — so budget disk space empirically per job rather than against a vendor number. On AMD: 2.2 (June 2026) added AMD GPU support (RDNA 3/3.5/4, mixed AMD+NVIDIA processing), but this is explicitly Windows-only; it does not change anything for the Linux CLI path. [Epic dev docs: RealityScan for Linux](https://dev.epicgames.com/documentation/realityscan/realityscan-for-linux?lang=en-US) · [Peter Falkingham: RealityScan 2.2](https://peterfalkingham.com/2026/06/25/realityscan-2-2-finally-brings-amd-gpu-support-to-windows/) · [Puget Systems: Hardware Recommendations for RealityScan](https://www.pugetsystems.com/solutions/photogrammetry-workstations/realityscan/hardware-recommendations/)

**Does it support GCPs / ground control?** Yes, and the workflow matches what this operator needs conceptually: a single GCP defines scene origin, two define origin and scale, three or more define full orientation, and each control point should ideally have measurements in at least three images. This is directly scriptable via the CLI commands listed above. [RealityScan Help: Georeferencing a Scene](https://rshelp.capturingreality.com/en-US/tutorials/georeferencing.htm)

### 3. The Windows-partition question

Given RealityCapture's Linux CLI is real but explicitly experimental, and the desktop GUI is Windows-only, the practical options for this dual-boot, single-GPU, production-Docker-stack machine are:

- **(a) Dual-boot switching.** Cheapest and technically simplest, but operationally the worst fit for the stated requirement: rebooting into Windows to run RealityCapture takes the Linux host — and everything in the 40-container production stack — offline for the duration. That is disqualifying for any pipeline step that must run unattended on a schedule, which is exactly what this operator is building. Usable only for occasional, deliberately-scheduled manual jobs, never for the automated pipeline itself.
- **(b) Windows VM with GPU passthrough, single GPU.** Technically achievable in 2026 using KVM/QEMU with VFIO and a tool like Looking Glass for low-latency display without a second monitor or dummy plug — this is a mature, well-documented community technique (multiple current guides and repos), not exotic. But single-GPU passthrough means **the GPU must be unbound from the Linux host and rebound to the VM for the duration of the Windows session**, which means the production Docker stack loses GPU access (if any containers use it) and the host desktop/compute environment is degraded while the VM holds the card. It is a real option, but it recreates most of dual-boot's downside (the GPU — the scarce resource RealityCapture needs — cannot be in two places generally at once) while adding real setup complexity (IOMMU groups, VFIO binding scripts, driver quirks) for a single-GPU box. Not a clean fit for an always-on automated pipeline; more viable as a scheduled, isolated batch window.
- **(c) Wine/Proton directly.** This is, in effect, what Epic's own Linux CLI build already does — RealityScan for Linux bundles its own isolated Wine environment rather than asking the user to run the Windows build under a manually configured Wine/Proton install. There is no evidence in this research of practitioners successfully running the full desktop RealityCapture GUI under a self-managed Wine/Proton setup for production work; Epic's own documentation warns against even using the GUI inside its bundled Wine layer. Treat "run it under Wine yourself" as functionally the same option as 3(a)/(b) above with less vendor support, not a distinct third path.
- **(d) A separate, cheap Windows box.** This is the option that actually satisfies both constraints — keeps the Linux production host untouched and gives RealityCapture a native Windows environment with a real, non-experimental GUI and CLI. It costs money (even a modest used workstation or mini-PC with a mid-range NVIDIA GPU), which cuts against "free," though the software itself stays free under the revenue threshold. It also reintroduces exactly the kind of manual, non-automated hand-off this operator is trying to design out of the pipeline, unless real engineering effort goes into remote-triggering it (e.g., a lightweight job queue that pushes datasets to the Windows box and pulls results back) — which is possible but is new infrastructure, not "free."

**Honest assessment: for the automated pipeline requirement specifically, none of these fully avoid disruption, and the Linux CLI path (already covered under Q1) is the only one of the four that doesn't cost either uptime, GPU availability, or new hardware/infrastructure.** If RealityCapture were the only way to get enterprise-grade orthomosaics, this would be the point where "this kills the automation requirement" applies to (a)/(b)/(c), and (d) would be the answer at the cost of some cash and some new plumbing. But since ODM already satisfies the automation requirement natively on the existing Linux host, this whole question is moot for the recommended path — it only matters if the operator later decides they specifically need RealityCapture's mesh/3D output for a job ODM can't handle. [GPU Passthrough Tutorial (GitHub)](https://github.com/snehilchatterjee/GPU-Passthrough-Tutorial) · [Looking Glass GPU passthrough walkthrough](https://quantum5.ca/2022/09/18/windows-vm-gpu-passthrough-part-3-setting-up-looking-glass/) · [Epic dev docs: RealityScan for Linux](https://dev.epicgames.com/documentation/realityscan/realityscan-for-linux?lang=en-US)

### 4. Head-to-head quality

Practitioner and comparison-source consensus in 2025–2026 places the tools roughly as follows, though I found no rigorous, numbers-driven benchmark specific to RealityCapture vs. ODM on the awkward cases (thin structures, vegetation, water, low overlap) — the evidence here is qualitative and secondary-source, not a controlled study:

- **Speed and mesh/geometry quality:** RealityCapture is widely reported as the fastest of the major engines thanks to GPU acceleration and efficient algorithms, and is described as producing "sharp geometry, excellent textures" — a 500-image dataset reportedly processes in 2–3 hours versus ODM's 4–6 hours on comparable hardware. [Aerocartwright: Photogrammetry on Linux comparison](https://aerocartwright.com/library/photogrammetry-linux-compared/)
- **Orthomosaic-specific maturity:** ODM is described as "built specifically for mapping — radiometric calibration, GCP handling, multi-band sensor support," with orthomosaic generation as its primary purpose, versus RealityCapture treating ortho export as secondary to 3D modeling. Metashape Professional is generally rated ahead of both on mesh depth when 3D output (not ortho) is the priority, at a cost this operator has already ruled out. [Aerocartwright: WebODM vs Pix4D vs Metashape vs RealityCapture](https://aerocartwright.com/library/pix4d-vs-metashape-vs-webodm-vs-realitycapture/)
- **ODM's known weak points**, corroborated in the earlier `orthomosaic-open-source-2026.md` research and unchanged by anything found here: straighter building edges and smoother DSM contours favor Pix4D by default (closeable by raising ODM's `pc-quality` setting, tracing to depthmap/point-cloud resolution rather than the compositing step); thin structures, water, and dense vegetation are where ODM degrades faster and with less diagnostic feedback than the commercial tools; image overlap remains the single largest lever for avoiding gaps and artifacts regardless of engine. No comparable, current, structure/water/vegetation-specific write-up exists for RealityCapture specifically — this is a real gap in available evidence, not a finding that RealityCapture handles these cases better or worse.
- **Production readiness on Linux specifically:** one source frames ODM as a "production workhorse" with over a decade of field testing on Linux, against RealityCapture's Linux CLI being "ready in 12–24 months" — i.e., an explicit practitioner judgment that RealityCapture's Linux path is not yet production-grade, consistent with Epic's own "experimental" labeling. [Aerocartwright: Photogrammetry on Linux comparison](https://aerocartwright.com/library/photogrammetry-linux-compared/)

### 5. The bottom line, restated with reasoning

Given everything above, switching the orthomosaic engine away from ODM is not worth the disruption, and ODM remains the right answer once automation and platform constraints are weighed against RealityCapture's actual, current state rather than its marketing framing.

The deciding factors, in order of weight:

1. **Automation reliability is the hard requirement, and ODM wins it outright.** ODM is native Linux, ships official Docker images, and already has a documented, three-layer scriptable interface (raw Docker CLI, NodeODM REST API, PyODM/CloudODM clients) that matches this operator's Mac-client-plus-Linux-GPU-host architecture with no vendor-imposed experimental caveats. RealityCapture's Linux path clears the bar technically (real CLI, real ortho/GCP commands, GPU requirement the 4070 SUPER satisfies) but is labeled experimental by its own vendor, needs a newer kernel than Ubuntu 24.04 ships by default, and carries at least one unverified but plausible report of headless authentication issues. Stacking "experimental" on top of "shares a host with a 40-container production stack and 77GB free disk" is exactly the kind of compounding operational risk a solo operator building unattended pipelines should not accept when a mature, native alternative already does the job.
2. **RealityCapture's strengths don't target this pipeline's actual gap.** Its edge is speed and mesh/geometry quality for 3D reconstruction — ground already covered by the operator's separate, already-committed splatfacto (Apache 2.0) gaussian-splatting choice. For the orthomosaic half specifically, RealityCapture's own ecosystem treats ortho as secondary, while ODM treats it as the primary deliverable. Switching engines to chase a strength that duplicates an already-solved problem, at the cost of the pipeline's most important property (unattended automation), is a bad trade.
3. **The free-tier risk profile differs.** ODM's AGPLv3 licence carries no revenue cap and no vendor-side authentication dependency; it cannot be revoked or re-priced by a business decision at Epic. RealityCapture's free tier is generous today but is, structurally, a vendor freemium offer tied to a revenue threshold and an online account — not a risk that matters much at a solo operator's current revenue, but worth naming as a longer-run dependency this operator doesn't currently have with ODM.
4. **Nothing else in the survey clears the bar.** Every other tool checked is either not free at any usable tier for a commercial deliverable (Pix4D, DroneDeploy, Metashape Professional, Site Scan, iTwin Capture, Correlator3D), free but explicitly non-commercial or missing georeferencing entirely (3DF Zephyr Free), or free but structurally incapable of the orthomosaic/GCP workflow at all (Metashape Standard). RealityCapture is genuinely the only credible non-open-source alternative this research surfaced, and it loses to ODM specifically on the automation axis, not on cost or raw capability.

**Recommendation:** stay on ODM as the pipeline's orthomosaic engine, exactly as the prior research concluded, with the fix already identified there (switch to still-image nadir grid missions with proper overlap) as the actual lever for the quality gap that matters. Optionally, keep a RealityCapture/RealityScan installation available on a normal Windows machine — not integrated into the automated pipeline — as a manual second opinion for a specific job where ODM's output looks wrong and it's worth the friction of a separate, non-automated run. Do not build automation around RealityCapture's Linux CLI until Epic drops the "experimental" label and a second independent practitioner source corroborates unattended, headless reliability over a real production period.

## Biggest risks / what would make this fail

- **Disk space is the sharpest immediate constraint, independent of which engine is used.** 77GB free on a shared NVMe is tight for photogrammetry: a single few-hundred-image 4K dataset can consume tens of gigabytes of intermediate point-cloud and mesh data during dense reconstruction, and running that alongside a 40-container production stack with its own storage churn raises real risk of an out-of-disk failure mid-job, or of a photogrammetry job starving the production stack. This applies to ODM and would apply at least as much to RealityCapture (which additionally needs space for its bundled Wine prefix and installation on Linux). Worth a deliberate capacity plan (a dedicated scratch volume, or moving processing to the idle 303GB NTFS partition via a reformat/repartition, or simply monitoring disk headroom as a pipeline precondition) before this becomes a production incident.
- **GPU contention with the production Docker stack.** If any of the ~40 production containers use the GPU, a batch photogrammetry job (ODM's SIFT stage, or RealityCapture's CUDA-mandatory reconstruction) will compete for it. This wasn't something this research could assess without knowing what the production stack does with the GPU, but it's worth checking directly before scheduling automated runs.
- **RealityCapture's "experimental" Linux label is a real, vendor-stated warning, not researcher caution.** If a future decision revisits RealityCapture for automation, treat Epic's own wording — "experimental," "not recommended... at your own risk" for the bundled Wine prefix — as the load-bearing fact, not the more optimistic single-practitioner report that the CLI "works fine."
- **Kernel version mismatch.** RealityScan's Linux CLI documentation states a minimum of kernel 6.14 (Ubuntu 24.04) or 6.10 (Fedora 39); Ubuntu 24.04 LTS's default GA kernel is older than that. Any future Linux CLI trial would need the HWE kernel or a manual upgrade — itself a change to a host that also runs a production stack, and a step that should not be taken lightly or without a rollback plan.
- **Freemium terms are a business risk that grows with success, not with the pipeline.** Nothing here suggests Epic is about to change RealityScan's free-tier terms, but a vendor-controlled revenue threshold is a real dependency this operator doesn't have with AGPLv3 ODM. Worth remembering if the business grows.
- **No RTK on the Mini 5 Pro is a universal constraint, not a tool-specific one.** Every tool in this survey — ODM included — depends on good ground-control-point practice for absolute accuracy, since the drone's own GPS is consumer-grade. This finding applies regardless of which engine ends up being used and was already the subject of the prior research's Phase 2 discussion.
