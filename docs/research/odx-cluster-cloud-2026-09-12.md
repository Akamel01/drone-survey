# ODX, ClusterODX, CloudODX judged against the pipeline design — 2026-09-12

Judged against: `docs/design.md` §§3, 4, 6; ADR 0006 (pipelines as declarative
manifests, thin runner, NodeODM does the orchestrating); ADR 0013 (rent GPU,
develop locally); ADR 0014 (compute placement ladder, decided before a job
starts, one job at a time today). Does not repeat what
[`webodm-ecosystem-2026-09-12.md`](webodm-ecosystem-2026-09-12.md) already
established (the April 2026 split, AGPL posture, WebODM-the-app being
irrelevant). This pass reads source and primary release notes, not the
SEO/blog content that has since sprung up around the split.

## Verdicts

| Tool | Verdict | What would change it |
|---|---|---|
| **ODX / NodeODX** | **Test** | Run one real Capture through NodeODX side by side with the NodeODM path already in use, and check `export-cog`'s output against the GDAL COG validator on ODX's actual result. Switching cost is near zero — the REST surface is byte-identical to NodeODM's — so the only thing worth testing for is whether ODX's `filter point` speedup (the one *quantified* change since the fork) is real on our own hardware and dataset. If it is, adopt; if not, no reason to move off ODM. |
| **ClusterODX** | **Ignore** | Revisit only if concurrency stops being deferred (design §3: "today one job runs at a time"). Even then it does not do what the placement ladder needs: it cannot be told "use this node" per request, only steered by adding/removing/locking nodes from its registry ahead of time — which means the Runner would end up doing the same placement work ADR 0014 already assigns it, just relayed through ClusterODX's node table instead of called directly. It would sit **beside** the Runner, not under or instead of it, and it imports exactly the kind of standing process, own data store, and scheduler-adjacent surface ADR 0006 draws the line at owning. |
| **CloudODX** | **Ignore** | It is a Go CLI, not a cloud provisioner — a REST client for NodeODX-compatible nodes, functionally equivalent to `curl`+the REST calls the Runner already makes. Nothing changes this verdict short of wanting a human-run ad hoc CLI instead of scripting the same three REST calls ourselves, which the design doesn't call for. |

## Evidence

### 1. ODX versus ODM, concretely

**What actually changed, from the fork's own release notes** (`gh api repos/WebODM/ODX/releases`, 10 releases, v3.7.0→v3.8.3, 2026-04-13 to 2026-09-04, 205 commits since the split):

- **v3.7.0** (the fork point): "Fixes, improvements, **6x build speed up**, update repos" and "Windows Fixes, NVIDIA RTX 50 Series Support, Checkpoints" — [PR #2](https://github.com/WebODM/ODX/pull/2), [PR #6](https://github.com/WebODM/ODX/pull/6). The "6x" figure is a **compile-time** speedup of the SuperBuild, not a processing speedup — worth being precise about, since it reads at a glance like a processing claim.
- **v3.8.0**: orthophoto merging parallelized by block ([PR #24](https://github.com/WebODM/ODX/pull/24)), Sentera 6X thermal camera support, OpenSfM/Obj2Tiles updated.
- **v3.8.2**: "**Reduce memory usage by ~50% in filter point stage, runtime by ~20%**" ([PR #33](https://github.com/WebODM/ODX/pull/33)) — this is the one genuinely quantified processing-speed claim in the whole changelog, from the maintainer's own commit message, scoped to a single stage (point filtering), not the pipeline end to end, and not compared against ODM on the same run.
- **v3.8.3**: removed the separate `--build-overviews` flag in favor of always folding overviews into `--cog` ([PR #35](https://github.com/WebODM/ODX/pull/35)), MicaSense RedEdge-P calibration fix, GSD now estimated from the bottom 10th percentile instead of the average, rolling-shutter readout time added for the DJI Lito X1, a GLB Draco-quantization fix.
- No dependency, algorithm, or default changed the shape of the pipeline (still OpenSfM → OpenMVS/MVE-style dense reconstruction → PDAL/GDAL rasterization) — these are the same libraries ODM lists in its own dependency set.

**No independent benchmark exists.** Search across GitHub issues/PRs and the web found none. The closest thing to a comparison is a marketing/SEO blog ([aerocartwright.com](https://aerocartwright.com/library/odm-vs-odx-2026-fork/)) which itself states plainly, with no numbers, that "the accuracy of your maps doesn't change. Both forks still call OpenSfM, OpenMVS, PDAL, and GRASS GIS" — i.e. even the marketing content declines to claim a measured difference. Confirmed by fetching the page directly, not by trusting a search snippet.

**The COG question, answered from code, with a real caveat.** `opendm/cogeo.py` (the function `export-cog` would ultimately be checking) is functionally identical between [WebODM/ODX](https://github.com/WebODM/ODX/blob/master/opendm/cogeo.py) and current [OpenDroneMap/ODM](https://github.com/OpenDroneMap/ODM/blob/master/opendm/cogeo.py) — diffed directly, the only differences are a renamed logging call and a parameterized (rather than hardcoded) DEFLATE predictor. The `gdal_translate -of COG ...` invocation itself is byte-for-byte the same template in both. **This means ODX has not changed the code path that produced the invalid COG this project already measured** (`docs/research/odm-first-run-2026-09-10.md`: NodeODM 2.2.4 / ODM 3.5.6, `cog` on by default, delivered file failed the GDAL COG validator — main IFD at a non-zero offset, striped rather than tiled, no overviews).

What *has* changed is the Docker base image, which is the more likely actual cause of that failure class: [OpenDroneMap/ODM#1864](https://github.com/OpenDroneMap/ODM/issues/1864) documents that ODM's GPU image, built on Ubuntu 20.04 with GDAL 3.0.4 (via a stale ubuntugis PPA), could not even recognize the `COG` driver ("Output driver `COG' not recognised") — closed 2025-07-24 by upgrading the image. ODX's current `Dockerfile` and `gpu.Dockerfile` both build on Ubuntu 24.04 (the GPU variant on `nvidia/cuda:12.9.1-devel-ubuntu24.04`), which carries a modern GDAL. Current upstream ODM's GPU build was also independently rearchitected (now `pixi`-based). So the specific hard failure in #1864 is very likely gone from both current ODX and current ODM — **but this project's own measured bug was a silent malformed-output failure, not a hard error, and no test was run in this pass against a live ODX container to confirm the newer GDAL actually emits a validator-passing file.** Given the code path is unchanged either way, the design's existing conclusion stands regardless of which engine is used: `export-cog` must stay a real Node that validates its own output, not a flag delegated to the engine.

**NodeODX's REST surface is the same as NodeODM's, confirmed by diffing the API docs, not by reading a description.** Fetched both `docs/index.adoc` files directly ([NodeODX](https://github.com/WebODM/NodeODX/blob/master/docs/index.adoc), [NodeODM](https://github.com/OpenDroneMap/NodeODM/blob/master/docs/index.adoc)) and diffed the endpoint lists: identical paths, including all four asked about — `POST /task/new`, `GET /task/{uuid}/info`, `GET /task/{uuid}/download/{asset}` (covers `all.zip`), `POST /task/remove`. The full parameter table for `POST /task/new` (the largest, most detail-bearing endpoint) is identical between the two docs down to the wording, except one typo fix ("pre-polulates" → "pre-populates"). `GET /info` gained an `engine`/`engineVersion` field in its response (NodeODX serves ODX, MicMac or LGT depending on config) but that is a response field, not a new required request parameter — nothing here would break code written against NodeODM.

**Published container images exist and are official**, confirmed from the repos' own READMEs and workflow badges, not a third party's claim: `webodm/odx` and `webodm/odx:gpu` on Docker Hub, built by ODX's own `publish-docker.yml`/`publish-docker-gpu.yml` GitHub Actions; `webodm/nodeodx` and `webodm/nodeodx:gpu` likewise, plus a native Windows bundle and an Apptainer path for rootless/HPC use documented in [NodeODX's README](https://github.com/WebODM/NodeODX/blob/master/README.md).

### 2. ClusterODX against the placement ladder

**Node selection is a scoring function, not a per-request pin**, read directly from [`libs/nodes.js`](https://github.com/WebODM/ClusterODX/blob/master/libs/nodes.js) (`findBestAvailableNode`): it filters to online, unlocked, non-autoscaled nodes whose `maxImages` covers the job, then sorts by smallest `maxImages`, then most free slots, then lowest queue count, then round-robin turn. There is no field in `POST /task/new` (checked [`libs/taskNew.js`](https://github.com/WebODM/ClusterODX/blob/master/libs/taskNew.js)) that lets a caller say "run this on node X" — the only lever is the node registry itself: `NODE LOCK`/`UNLOCK`/`ADD`/`REMOVE`, available both over a telnet admin CLI and, more usably for automation, over an HTTP admin API on the status port (`POST /r/node/add`, `/r/node/lock`, `/r/node/unlock`, `GET /r/node/list`, in [`adminweb.js`](https://github.com/WebODM/ClusterODX/blob/master/adminweb.js)). So our own rule *can* drive placement, but only by having the Runner manage ClusterODX's node table before every submission (lock everything except the intended target, or add/remove nodes as they come online) — which is strictly more moving parts than the Runner just calling the chosen NodeODX host directly, since the Runner already has to know and reach that host per ADR 0014.

**Nodes coming and going is supported at the infrastructure level**: `nodes.js` polls each registered node's `/info` on a 60-second interval and marks it online/offline; a `NODE LOCK` on a node prevents auto-selection without removing it. That matches "a borrowed GPU that's sometimes there" reasonably well as a mechanism — the friction is that ClusterODX's own concept of "available" (online + unlocked + has queue slots) is coarser than ADR 0014's ("reachable, inside the permitted window, and the card actually free"), so the availability check the design already commits to building would still have to live in the Runner, on top of whatever ClusterODX reports.

**What it needs to run**: Node.js — the README states "14 or earlier... has compatibility issues with NodeJS 16 and later," and the repo's own `.nvmrc` pins **15.10.0**, which is itself past end-of-life and inconsistent with the README's own "14 or earlier" claim — a genuine wart, not an inference. `package.json` pins `express@^4.16`, `axios@^0.18`, `aws-sdk@^2.466` — all multi-year-old majors. No database; state is a JSON file on disk (`saveToDisk`/`loadFromDisk` in `nodes.js`). It runs as one always-on Node process (reverse proxy + admin web + optional telnet CLI); a `docker-compose.yml` and a systemd unit (`services/clusterodx.service`) are provided for that purpose.

**Autoscaling exists but targets the wrong shape of "rented GPU."** `libs/asr-providers/` has `digitalocean.js`, `hetzner.js`, `scaleway.js`, `aws.js`, plus `LightningCloudProvider.js` (UAV4GEO's own paid backend) and a `LocalCloudProvider.js`. All of the VM-based providers work through `docker-machine`, which is itself a discontinued upstream project (as already recorded in the prior report). `aws.js` does support GPU instances and spot requests (`--gpus all`, `--amazonec2-request-spot-instance`, read directly from source), so it isn't CPU-only — but the whole point of ADR 0013's rented-GPU fallback is renting a box by hand from whichever provider is cheapest that hour and pointing the Runner at it; ClusterODX's autoscaling wants to own the full VM lifecycle itself via a specific, narrow set of drivers. The two models don't compose — using ClusterODX for renting means adopting its provider list and its VM-lifecycle code instead of the Runner's own; using it only as a static NODE ADD target for a manually-rented box works, but then it is adding nothing (see above).

**Net placement**: ClusterODX would sit **beside** the Runner, not under or instead of it — it does not remove the placement decision, the availability check, or the data-transfer responsibility from the Runner; it adds a second, coarser copy of the first, running as its own aging Node.js service. That is duplication, not delegation, which is the opposite of what ADR 0006 asks for.

### 3. CloudODX against the rented-GPU fallback

**What it actually is**: a Go CLI (`go get github.com/WebODM/CloudODX`), read directly from its [README](https://github.com/WebODM/CloudODX/blob/master/README.md) and `public_nodes.json` — a thin REST client for NodeODX-compatible nodes, not a cloud VM provisioner. `odx path/to/images --dsm` uploads to a node and downloads results; that's the entire feature set beyond option/GCP handling that mirrors what NodeODX's API already exposes.

**What service it talks to, and whether it costs money**: by default, with no node specified, it talks to `spark1.webodm.net`, the sole entry in `public_nodes.json`, maintained by UAV4GEO — the operator of **WebODM Lightning** (webodm.net), the paid, proprietary-LGT-engine hosted service already identified in the prior report. Fetched webodm.net directly: new users get 150 free credits, then it is pay-as-you-go. So **the default target is a metered commercial service**, not a free community resource.

**It is not vendor-locked**: `odx node add mynode http://address:port` followed by `odx -n mynode ...` points CloudODX at any NodeODX-compatible node, including one running on a GPU rented from an arbitrary provider — CloudODX has no opinion about what's underneath the node it's talking to, since it only speaks the NodeODX REST API. It would work equally well against our own NodeODX/NodeODM container on a rented box.

**Licence, confirmed from the file, not the badge**: `LICENSE` in [WebODM/CloudODX](https://github.com/WebODM/CloudODX/blob/master/LICENSE) is the full GNU **GPL v3** text (not AGPL) — matches GitHub's own `license.spdx_id: GPL-3.0` field. What that means for us: plain GPL-3.0's copyleft is a *distribution* trigger, not AGPL's *network-use* trigger — it activates when you convey the software or a modified/combined version of it to someone else, and it has no clause at all about running it as a network service. Invoking the unmodified released `odx` binary as a separate CLI subprocess (never linking it into our code, never redistributing it) triggers nothing; if anything this is a strictly lighter obligation than the AGPL already governing ODM/NodeODM in this same pipeline, which we already treat as fine as an unmodified, unexposed separate process.

## Could not verify

- Whether ODX's current Docker images actually emit a GDAL-validator-passing COG on a real orthophoto — the code path is unchanged from ODM and the base image is newer, but no container was run in this pass to confirm the silent-malformed-output failure this project measured is actually gone.
- Any third-party, reproducible benchmark of ODX vs ODM on identical input, from any source — none exists as of this writing.
- Whether NodeODX's `/options` list has grown any ODX-specific processing options beyond what's in NodeODM's — the endpoint and its schema are identical, but the *contents* of the options array (which comes from ODX's own `argparse` definitions) were not diffed flag-by-flag in this pass.
- Real-world throughput of ClusterODX's HTTP admin API (`/r/node/add`, `/r/node/lock`) under a script driving it once per job — read from source, not exercised against a running instance.
- Whether `docker-machine`'s GitLab-maintained fork still actually works against current DigitalOcean/Hetzner/Scaleway/AWS APIs — flagged as a risk in the prior report and not re-tested here.
