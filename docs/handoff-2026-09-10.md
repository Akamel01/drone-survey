## 1. Why this handoff exists

The current session was executing a narrow, single-machine (MacBook Air M1, CPU/Metal-only) proof-of-concept pipeline: DJI Mini 5 Pro footage → COLMAP (SfM) → OpenSplat (Gaussian Splat) → OpenMVS (dense/mesh, CUDA-free). **Do not just resume the old shell pipeline.** Treat the work below as background/context; the actual task is designing the new stack per the requirements in §3.

## 3. What the new session must actually do

The user wants to **redesign the entire stack from scratch** as a professional aerial-survey production system, not extend the POC. Requirements, verbatim intent preserved:

### 3.1 Product bar
- Outputs must be **efficient, high-accuracy, high-precision**, and look like what professional aerial-survey companies deliver to paying clients: professionally rendered/color-graded 3D models, **orthomosaic maps**, and **3D timelapses** (e.g., a construction site surveyed weekly, shown evolving over time).
- Modeling technique: **Gaussian Splatting and/or photogrammetry** — both should be first-class, not one bolted onto the other.
- Current drone: **DJI Mini 5 Pro**. Future: the user will add **GCPs (Ground Control Points)** for survey-grade georeferencing — the architecture should anticipate this (GCP ingestion/alignment step) even if not implemented yet.

### 3.2 Pipeline architecture
- **Separate automated pipelines per purpose** (e.g., a Gaussian-Splat pipeline, a photogrammetry/orthomosaic pipeline, a timelapse-compositing pipeline) — not one monolith.
- Pipelines are **node-based**; nodes must be designed cleanly, avoiding redundant/duplicated logic across pipelines — proper software architecture (shared libraries/services for common steps like frame extraction, undistortion, georeferencing, not copy-pasted per pipeline).
- Whatever orchestration tech is chosen must be **streamlined and controllable from the command line** — CLI-first, not GUI-dependent for triggering/operating runs.

### 3.3 Viewing/editing
- Rely on an **open-source 3D viewer/editor** that's feature-rich, for the user to inspect results locally, and same tool (or its output format) should be embeddable in a future client-facing website (deliver models, videos, images, reports to clients).

### 3.4 Compute topology — this is a major architecture driver
- User has **two machines**: this MacBook Air (M1) and a **Linux machine with an NVIDIA GPU**. Both on the same LAN via Ethernet, and both on the same **Tailscale** account (so a stable private network path exists regardless of LAN).
- Intent: **delegate almost all heavy compute to the Linux/NVIDIA box** — CUDA-accelerated COLMAP dense stereo, GPU-accelerated Gaussian Splat training (the real target, not Mac Metal, which was only a stopgap for the POC), etc. The Mac becomes primarily a control/orchestration/light-viewing client.
- Architecture must define: how jobs get dispatched to the Linux node (queue? SSH+scripts? remote orchestrator agent? job runner exposed over Tailscale?), how results/artifacts come back, and how this fits the CLI-first requirement above.

### 3.5 Future website
- A **developer tab** with an **n8n-style visual graph** of the pipelines (nodes + links), for the user to *see* pipeline structure/state.
- Phase 1: **visualization only**. Phase 2 (later, not now): full interactive control from that UI.
- Also (per §3.3) a client-facing area to deliver models/videos/images/reports.

### 3.6 Process requirements for the next session
- **Use the `grill-with-docs` skill** to run this as a proper "gilling" (deep-dive) research + documentation session.
- **Use the `wayfinder` skill** for long-horizon planning — this is explicitly a multi-phase, multi-month buildout, not a single sprint.
- **Do real web research** (state-of-the-art check) before committing to a stack, covering: pre-processing, processing (SfM/MVS/Gaussian Splat), modeling, editing/directing, post-processing (color grading/toning), rendering, filtering/cleaning, and client-presentation channels/methods used by actual professional aerial-survey outfits in 2026. Don't assume the POC's tool choices (COLMAP/OpenSplat/OpenMVS/CloudCompare/QGIS/Blender) are still the right ones for a from-scratch, GPU-node-backed, multi-pipeline architecture — re-evaluate with fresh eyes, including newer Gaussian-Splat variants, distributed/remote GPU orchestration patterns, and orthomosaic/timelapse-specific tooling.
